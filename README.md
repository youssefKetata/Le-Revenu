# Communauté Le Revenu

Technical assignment: a community forum built with Next.js App Router, React, TypeScript, Tailwind CSS, Strapi v5 and PostgreSQL.

## Current scope

Phases 1 and 2 are complete: the applications, PostgreSQL connection, forum schemas, repeatable demo seed and public read API are verified. The frontend currently shows a small French placeholder page. Login, secure publishing and forum screens are planned in the [implementation plan](IMPLEMENTATION_PLAN.md).

```text
frontend/                 Next.js application
backend/                  Strapi v5 application and database configuration
scripts/setup-env.mjs     Creates local environment files and random secrets
scripts/check-database.mjs Verifies the configured application database connection
scripts/seed-demo.mjs     Loads Strapi and runs its demo seed
```

Next.js communicates with Strapi over HTTP. Strapi owns all content, business rules and database access. The database-check script is a developer diagnostic, outside the Next.js application.

## Prerequisites

- Node.js 24 LTS and npm.
- A running PostgreSQL server. This machine uses the existing PostgreSQL 18.1 Windows service on port 5432.
- PostgreSQL administrator access for the initial creation of a dedicated database and restricted application role.

No Docker, separate database server, cloud account, Redis or additional runtime is required.

## Installation on a fresh checkout

Run from the repository root:

```powershell
npm --prefix frontend ci
npm --prefix backend ci
npm run setup:env
```

`setup:env` copies the committed environment examples and generates random local passwords and signing secrets. It preserves existing `.env` files and never prints secret values. Real environment files are ignored by Git.

Create an application role and database in your existing PostgreSQL installation. For example, open SQL Shell / psql as the local PostgreSQL administrator:

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h 127.0.0.1 -U postgres -d postgres
```

Then run in psql:

```sql
CREATE ROLE le_revenu LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password le_revenu
CREATE DATABASE le_revenu OWNER le_revenu;
\q
```

At the password prompt, use the generated `DATABASE_PASSWORD` from `backend/.env`. Alternatively, choose a password and update `backend/.env` to match. The administrator password is only used by psql during setup; the application uses the restricted `le_revenu` role.

For an existing project database, skip creation and update `backend/.env` with its connection settings. The script does not reset passwords or modify existing databases.

Verify connectivity after installing backend dependencies:

```powershell
npm run db:check
```

The output includes the database name, application role and PostgreSQL version, without passwords.

## Development

Ensure your existing PostgreSQL service is running. On this machine, `le_revenu` and its restricted role have already been created; no database initialization command is needed on subsequent runs.

Open two terminals in the repository root.

Terminal 1:

```powershell
npm run dev:backend
```

Terminal 2:

```powershell
npm run dev:frontend
```

- Frontend: http://localhost:3000
- Strapi admin: http://127.0.0.1:1337/admin
- Strapi health: http://127.0.0.1:1337/_health (HTTP 204)
- Frontend connection check: http://localhost:3000/api/health

On the first Strapi admin visit, create a local administrator account. This is distinct from the forum demo-member accounts described below. Do not commit admin credentials.

The frontend connection check returns HTTP 200 when Next.js can reach Strapi, or HTTP 503 when Strapi is unavailable. It does not perform an independent database query; Strapi initializes its database connection at startup. Use `db:check` for the direct database diagnostic.

Stop application processes with Ctrl+C. Your existing PostgreSQL Windows service stays under its normal Windows service management.

## Demo data

After database setup, stop any running backend process and run from the repository root:

```powershell
npm run setup:env
npm run seed:demo
```

The seed compiles the backend TypeScript, loads Strapi and writes through its native user service and Document Service API. It does not start an HTTP server or build the admin UI. Seeding is explicit; normal application startup does not run it.

It creates two confirmed members with the Authenticated role, four French categories (Bourse, Immobilier, Épargne and Fiscalité), five discussions and five replies. The final discussion has no replies. Sample text is fictional and contains no real member information.

| Username | Email | Password in local `backend/.env` |
| --- | --- | --- |
| `camille_demo` | `camille.demo@example.test` | `DEMO_CAMILLE_PASSWORD` |
| `thomas_demo` | `thomas.demo@example.test` | `DEMO_THOMAS_PASSWORD` |

Passwords are generated by `setup:env`, hashed by Strapi when accounts are created, and never logged by the seed. You can set your own values before the first seed (at least 12 characters and at most 72 UTF-8 bytes). These are forum accounts, not dashboard administrators; the public login flow comes in phase 3.

The seed creates missing records and keeps existing ones, including edited content, relations, roles and password hashes. Stable document IDs are the only seed identifiers, including after titles, usernames or slugs change. Username/email collisions with a different user cause an error; category slug collisions are rejected by the schema. All seed writes run in one transaction and roll back together on failure.

Rerun the same command to fill in missing demo records. It does not reset the database, restore edited values or reset existing passwords when environment values change. Forum API permissions are configured separately by Strapi's startup bootstrap. After seeding, start Strapi and inspect the entries in Content Manager.

## Forum content model

The versioned schemas live under `backend/src/api/<name>/content-types/<name>/schema.json`:

| Collection | Fields and relationships |
| --- | --- |
| Category | Required name and unique slug (generated from the name); optional description, icon key and six-digit hex color; many discussions |
| Discussion | Required title (10-255 characters), plain-text content and type (`question` or `discussion`); one author, one category and many replies |
| Reply | Required plain-text content; one author and one discussion |
| User | Native Users & Permissions user, extended with many discussions and replies |

`backend/src/extensions/users-permissions/strapi-server.ts` adds the inverse author relationships while preserving the plugin's native authentication fields. Forum members are distinct from Strapi administrators.

Draft & Publish is disabled on all three forum collections. Contributions have a single immediately visible version; `createdAt` is the publication date used by the forum. Strapi supplies timestamps and `documentId` values.

Start Strapi and open its Content Manager to see Category, Discussion, Reply and User. Strapi synchronizes their tables and relations to the configured project database at startup. The schemas define storage; the controllers, services and routes implement the read API below. Whitespace validation, authenticated author assignment and other publishing rules will be implemented in phase 3.

After changing schemas or the user extension, regenerate the checked-in backend types:

```powershell
npm --prefix backend run strapi -- ts:generate-types
```

## Public read API

Start Strapi with `npm run dev:backend`. The API base URL is `http://127.0.0.1:1337/api`.

| Method and path | Purpose | Query parameters |
| --- | --- | --- |
| `GET /categories` | Categories with names, slugs, descriptions, icon keys and colors | `page`, `pageSize` |
| `GET /discussions` | Discussion summaries with author, category, date and reply count | `category` (slug), `sort` (`newest` or `oldest`), `page`, `pageSize` |
| `GET /discussions/:documentId` | Discussion content and summary fields | None |
| `GET /discussions/:documentId/replies` | Replies for one discussion, oldest first | `page`, `pageSize` |

Example: `http://127.0.0.1:1337/api/discussions?category=bourse&sort=newest&page=1&pageSize=10`.

Lists return `{ data: [...], meta: { pagination: { page, pageSize, pageCount, total } } }`. Detail returns `{ data: { ... }, meta: {} }`. Pagination defaults to page 1 and 25 records, allows at most 100 records per page, and rejects offsets above 100,000. Valid pages beyond the last page return an empty list with the matching total; unknown category slugs return an empty list. Dates use `createdAt`, with `documentId` as a stable tie-breaker. Categories are sorted by name.

The feed returns `documentId`, `title`, `type`, `createdAt`, `author`, `category` and `replyCount`. Only detail includes discussion `content`. Replies return `documentId`, `content`, `createdAt` and `author`. Author projections contain only `documentId` and `username`; user emails, credentials, roles and tokens are never included. Deleted authors or categories are represented by `null`. Numeric database IDs are not part of this API contract.

Queries fetch explicit fields and relations through Strapi's Document Service. Reply counts use Strapi's count-only relation population, which runs one grouped count for the page instead of fetching reply bodies or counting each discussion separately. Replies are fetched and paginated independently. Reads send `Cache-Control: no-store` so dashboard edits appear on the next request.

Invalid numbers, malformed document IDs and unsupported query options return HTTP 400. Missing discussions return HTTP 404, including on the replies route. Arbitrary `fields`, `populate`, `filters` and search parameters are not accepted by this focused API.

`backend/src/permissions/forum.ts` runs at startup and reproducibly grants these four read actions to Public and Authenticated members. It removes other forum action grants and end-user account-management grants from those roles. User-directory endpoints remain forbidden (HTTP 403); dashboard administrator permissions are separate. Self-registration is disabled because this project uses seeded members. No forum write routes exist in phase 2 (HTTP 405); authenticated publishing comes in phase 3. Code owns these settings, so changing forum permissions only in the dashboard is not a persistent configuration change.

## Checks and production-mode startup

Run checks and builds sequentially on an 8 GB machine:

```powershell
npm run lint:frontend
npm run typecheck:frontend
npm run typecheck:backend
npm run test:seed
npm run test:api
npm run build:backend
npm run build:frontend
```

After successful builds, the applications can be run in separate terminals:

```powershell
$env:NODE_ENV = 'production'
npm run start:backend
```

```powershell
npm run start:frontend
```

Stop development processes before running production builds. The Strapi database pool is limited to three connections for local development. Production mode avoids keeping development watchers active when only a demonstration is needed. Seed and read-API integration tests are available now; publishing and frontend tests will accompany those features.

Use a new terminal for `dev:backend`, or set `$env:NODE_ENV = 'development'` when switching that terminal back to development.

## Configuration and boundaries

- Backend environment template: `backend/.env.example`.
- Frontend environment template: `frontend/.env.example`.
- Backend database configuration: `backend/config/database.ts`, PostgreSQL only.
- `STRAPI_URL` is server-side configuration. Never place database credentials or privileged Strapi tokens in `NEXT_PUBLIC_*` variables.
- The placeholder page uses system fonts so startup/build does not require an external font download. Typography will be refined during the design phase.
- Dependencies for the two applications are installed separately, with their own lockfiles; Strapi's admin React version is independent from the Next.js frontend.
- Strapi content-type schemas will be committed to Git. Its application database tables are initialized through Strapi; no hand-written forum SQL schema is used.

## Demo seed verification

Run the automated integration test with:

```powershell
npm run test:seed
```

It uses the configured PostgreSQL database, creates an empty schema with a random test-only name, and removes that schema in cleanup. The database role must be able to create schemas, as the database owner from the installation instructions can. The test checks fresh creation, password hashes, relations, the unanswered discussion, reruns, preserved edits, identity collisions and rollback after partial failure. Existing application data is kept in its own schema.

- The first local run created two members, four categories, five discussions and five replies. A second run created no records.
- Seed lookups use fixed document IDs only. Username/email and category-slug collisions with different documents are rejected without changing existing records.
- The stored passwords validate through Strapi's native password service; member roles, confirmation status, author/category/discussion relations and the unanswered discussion were checked.
- Transactional checks confirmed that reruns preserve edited content, usernames, slugs, password hashes, account status, roles and relations. The temporary edits were rolled back.
- Omitting the second new member's password rolled back the first account creation. A deleted demo reply was recreated by the CLI with its expected content and relations; shutdown completed cleanly.
- Environment setup preserves existing values and leaves the file unchanged on a second run. Backend type checking and the seed/setup script syntax checks pass.

## Read API verification

`npm run test:api` starts the real Strapi HTTP server on an ephemeral port in an isolated PostgreSQL schema, seeds it, and removes the schema in cleanup. The eight test results cover:

- Safe feed/detail/category payloads and reply counts, including a discussion without replies.
- Backend filtering, both date sort orders, stable ties, pagination and empty results.
- Independently paginated replies; malformed and unsupported queries; coherent HTTP 400/404 errors.
- A single grouped reply-count query for both one-record and five-record feed pages, with the same total number of SELECT queries.
- Public/member reads, blocked user-directory access and write methods, disabled registration, and repeatable permission configuration.
- Successful reads after dashboard deletion of an author or category.

The test database role needs schema-creation permission, as for `test:seed`. Existing application data is kept in its own schema.

A local smoke check against the actual project database also returned HTTP 200 for categories, filtered/paginated discussions, discussion detail and paginated replies, with the expected seeded totals. Backend type checking and the existing seed integration test pass.
